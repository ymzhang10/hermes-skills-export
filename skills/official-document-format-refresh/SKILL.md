# Official Document Format Refresh

## 适用场景

当用户提出以下需求时使用：

- “把这个机关公文排成标准格式”
- “按党政机关公文格式刷新一下”
- “这个旧 doc 帮我整理成规范公文版式”
- “不要改内容，只改成正式公文格式”
- “按最新公文格式重排成 Word”

适用于：

- 旧 `.doc` / `.docx` 公文整理
- 普通文本转规范机关公文版式
- 需要输出可继续在 Word 中编辑的 `.docx`

不适用于：

- 用户明确要求严格复刻某单位自定义红头模板、专用套红、专有页眉页脚、固定章位图像
- 用户要求修改政策表述、代拟公文内容、判断行文权限
- 扫描件 OCR 质量很差且正文无法可靠恢复的情况

## 执行依赖

执行本 skill 前，先加载 `docx` skill 作为 `.docx` 读写、拆包、重打包、转换、兼容性处理的底层能力来源；本 skill 只负责机关公文场景下的规范判断与版式刷新。

如任务涉及 legacy `.doc`、复杂 `.docx` 兼容、图片/批注/修订痕迹、XML 级编辑、LibreOffice 转换、pandoc 抽取、打包校验等，优先遵循 `docx` skill 的工具链与约束。

## 核心原则

1. **只刷新格式，不擅改原文内容。**
2. **保留原有层级和语义。** 只在必要时做段落拆分、空行清理、编号识别。
3. **输出新文件。** 不覆盖原始 `.doc` / `.docx`。
4. **先抽取文本，再重建版式，再核对文本一致性。**
5. **有歧义先问。** 尤其是：这是“普通公文 / 红头文件 / 信函式公文 / 上行文 / 联合行文”中的哪一种。

## 规范解释总则（防止把示例写法误当规范要求）

1. **示例写法不自动等于强制规范。** 原始材料中出现的示意排版、示例条目、占位文本、说明性括注，只能作为识别参考，不能自动升格为必须执行的格式要求。
2. **规范条文优先于示例展示。** 若同一材料中“示例页/示意写法”和“后文正式条文”存在差异，优先按明确条文执行，并在必要时向用户说明冲突点。
3. **保守识别不等于规范推荐。** 某种写法若只是为了兼容现实原稿识别（如非标准编号、口径不一的落款写法），只能作为保守识别模式，不能写成推荐输出格式。
4. **未明确写出的效果不得擅自补足。** 规范未写“加粗/加黑/居中/右对齐/空几行/改编号体系”等，就不得因为“看起来更像公文”而自动补上。
5. **遇到来源冲突时先保守，不扩张解释。** 如不同段落对同一规则表述不完全一致，默认采取更少改动、更多保留原文的解释路径；必要时先问用户。

## 依据的关键规范点（执行时必须内化）

### 页面与版心

- 用纸：A4（210mm × 297mm）
- 天头：37mm
- 订口：28mm
- 版心：156mm × 225mm（不含页码）
- 发文机关标志上边缘至版心上边缘：
  - 普通公文：25mm
  - 上报公文：80mm

### 字体字号

- 标题：2号小标宋（常见替代：方正小标宋简体；缺字库时再与用户确认替代字体）
- 主送机关：3号仿宋
- 正文：3号仿宋
- 一级标题：3号黑体（仅指定黑体，不默认加粗；除非原始规范或用户明确要求）
- 二级标题：3号楷体
- 三级/四级条目：3号仿宋
- 签发人标签：3号仿宋
- 签发人姓名：3号楷体
- 页码：4号半角白体阿拉伯数字（实际工具不支持时，尽量接近并向用户说明）

### 正文层级顺序

严格按以下顺序识别：

1. `一、`
2. `（一）`
3. `1.` 或 `1．`
4. `（1）`

### 标题与正文排布

- 标题位于红色反线下空两行，居中，可分一行或多行
- 主送机关位于标题下空一行，左侧顶格，末尾加全角冒号
- 正文位于主送机关下一行
- 每自然段左空2字，回行顶格
- 数字、年份尽量不拆行
- 一般每面22行，每行28字

### 附件、附注、落款

- 附件说明：正文下空一行，左空2字写 `附件：`
- 发文机关署名：署全称或规范简称
- 成文日期：正文下空两行，右空4字；年、月、日用汉字标全，`零` 写 `○`
- 附注：如有联系人、电话等，置于成文日期下一行，左空2字加圆括号

### 印章与联合行文

- 单一机关：印章端正、居中、下压成文日期
- 联合行文：主办机关印章在前
- 多印章时不得相交或相切
- 如页面剩余空白放不下印章，通过调整行距字距处理，**不得**用“此页无正文”规避

### 版记

- 抄送机关
- 印发机关
- 印发日期
- 版记各要素下加反线，宽度同版心

### 新旧规范差异（必要时提醒用户）

- 2012 年起党政机关公文处理规范统一
- 文种增至 15 个（增加“决议”“公报”）
- **取消主题词**
- 行政公文也应署发文机关名称

## 正文保护协议（高优先级，执行时必须优先于排版优化）

### 禁止行为

以下动作一律禁止，除非用户明确要求修改正文内容：

1. 不得润色、改写、压缩、扩写、重组原文表述。
2. 不得把口语改成书面语，不得把短句改成长句，也不得反向简化。
3. 不得擅自修正政策表述、机关名称、职务称谓、时间、数字、标点含义。
4. 不得为了“更像公文”而补写过渡句、结束语、套话、依据、附件标题。
5. 不得自行补造密级、紧急程度、签发人、发文字号、主送机关、抄送机关、印发机关。
6. 不得合并或拆分正文段落，除非该操作只是恢复原始断行错误，且不改变文字顺序与内容。
7. 不得把正文中的旧编号体系私自改写成新编号体系；只能在排版层面识别，不得改写文字本身。
8. 不得把规范中仅指定的字体自动升级为“字体 + 加粗”样式。例如“黑体”不等于“加粗黑体”；凡标准未写“加粗/加黑/着重”，一律按未加粗执行。

### 允许行为

以下动作视为“格式刷新”而非“改正文”：

1. 清理由转换工具引入的 `PAGE`、多余空行、异常换页残留。
2. 在不改变文字内容的前提下恢复明显断裂的同一句误换行。
3. 按段落语义套用字体、字号、缩进、对齐、间距。
4. 仅当原文已经通过明确标签或稳定版式清楚标识该区域（如明确出现“附件：”“抄送：”等）时，才允许做**机械归位**；凡是需要基于语义猜测把某段改放到标题、主送机关、正文、附件说明、落款、版记等其他区域，均视为**内容移动**，默认禁止。
5. 在核对阶段标记疑似原文问题，但不得直接改入输出稿。

### 中止条件

遇到以下任一情况，必须先问用户，不能继续“自动刷新”：

- 原文存在明显错别字/病句，但用户未授权改正文
- 原文段落边界不清，拆分后可能改变语义
- 同一段可能既像正文又像附件说明/版记
- 原文缺失关键字段，补写会构成内容新增
- 需要把某段从原位置移动到另一功能区域（如正文→附件说明、正文→版记、正文→落款）
- 发现多个可能版本的标题、署名、日期，无法可靠判断

### 正文保护核对清单

生成前后必须逐项自查：

- 文字是否一字未擅改
- 数字、日期、机关名称是否一字未动
- 标点是否未被自动替换成另一种含义
- 段落顺序是否完全一致
- 仅有的差异是否限于空行、转换残留、无语义空白归一

对外汇报时，必须单独报告：

- “本次是否 100% 只刷新格式、未改正文”
- 如否，具体改了哪几处、为什么、是否得到用户授权

## 实验验收：正文零改动自动判定

为保证对比实验可信，执行本 skill 后必须产出“正文零改动”判定结论。

### 必做步骤

1. 提取源文件文本与输出文件文本。
2. 做归一化处理后执行 diff。
3. 将 diff 结果纳入最终汇报。

### 允许忽略的差异（仅限以下几类）

- `PAGE` 等转换残留
- 文末多出或缺少的空白行
- 连续空格归一
- 不承载语义的换页残留

### 默认判定为“改正文”的差异

只要出现以下任一情况，默认判定为“未通过正文零改动验收”：

- 任意汉字、数字、字母发生增删改
- 标点符号发生有语义影响的变化
- 段落顺序变化
- 某段从一个功能区域移动到另一功能区域
- 自动补入标题、主送机关、附件说明、署名、日期、版记等文本

### 汇报要求

最终汇报必须包含：

- `正文零改动验收：通过 / 未通过`
- 若未通过，列出全部差异并说明是否已获用户授权
- 若通过，说明忽略了哪些无害差异

### 推荐 diff 脚本

```bash
python3 - <<'PY'
import subprocess, re, difflib, sys

def norm(path):
    txt = subprocess.check_output(['textutil', '-convert', 'txt', '-stdout', path], text=True)
    txt = txt.replace('\r\n', '\n').replace('\r', '\n').replace('\xa0', ' ')
    lines = []
    for ln in txt.split('\n'):
        s = ln.rstrip()
        if re.fullmatch(r'PAGE\s*\d*', s.strip()):
            continue
        lines.append(re.sub(r'[ \t]+', ' ', s).strip())
    while lines and lines[-1] == '':
        lines.pop()
    return lines

src = norm(sys.argv[1])
out = norm(sys.argv[2])
passed = (src == out)
print('正文零改动验收：' + ('通过' if passed else '未通过'))
for line in difflib.unified_diff(src, out, fromfile='src', tofile='out', n=1):
    print(line)
PY source.doc formatted.docx
```

## 推荐工作流

### 第 1 步：判断输入类型

先判断用户给的是：

- `.doc`
- `.docx`
- 纯文本
- PDF / 扫描件

若是扫描件或图片，优先加载 OCR 相关 skill；若是 `.doc/.docx`，继续本流程。

### 第 2 步：抽取文本

#### 旧 `.doc`

在 macOS 上优先用：

```bash
textutil -convert txt -stdout source.doc
```

如需先转可读的 OOXML：

```bash
textutil -convert docx source.doc
```

#### `.docx`

可直接用 `python-docx` 读取，或先用 `textutil` 抽纯文本核对。

### 第 3 步：清洗文本

必须做：

- 统一换行符
- 去掉 `PAGE` 等转换残留
- 清理多余空白行
- 识别标题、主送机关、正文层级、附件说明、落款、日期、附注

注意：

- 不得偷改原文措辞
- 不得自行补政策内容
- 只做最小必要的段落归位

### 第 4 步：识别文种与版式等级

优先识别：

- 是否为上行文（决定签发人、机关标识高度等）
- 是否为信函式公文
- 是否为联合行文
- 是否存在附件、附注、抄送、印发机关信息

如果这些判断会显著影响排版且无法从原文可靠推出，必须先问用户。

### 第 5 步：重建 `.docx`

优先使用 `python-docx` 生成新的 `.docx`，不要写 `.doc`。

#### 基础要求

- A4 页面
- 合理设置页边距，尽量逼近规范版心
- 所有中文 run 都设置 `w:eastAsia` 字体
- 标题居中
- 正文首行缩进约 2 字符
- 按层级应用不同字体
- 附件说明、附注、落款、日期分区清晰

#### 常见段落分类规则

可按以下正则保守分类：

- 首行：标题
- 第二行若形如 `（……）`：副标题/日期式说明
- `^一、`：一级标题（黑体）
- `^（一）`：二级标题（楷体）
- `^\d+[.．]`：三级条目（仿宋）
- `^（\d+）`：四级条目（仿宋，规范层级）
- `^\d+、`：原稿中可能出现的保守识别模式，但**不视为规范推荐四级层级**，不得据此自动改写编号体系
- `^附件：`：附件说明
- `^抄送：`：抄送区
- 日期、署名、附注、联系人电话：仅在原文已有明确标签或稳定格式信号时，才可按落款/附注区机械识别；否则不得靠语义猜测自动归位
- 其他：正文（仿宋，首行缩进）

### 第 6 步：输出文件

- 默认输出到：`/Users/ymzhang/Obsidian-Local/ymzhang/hermes-backup/`
- 新建文件名使用：`主题_YYYY-MM-DD_HH-mm-ss.docx`
- 不覆盖原文件

### 第 7 步：核对一致性

生成后必须做文本核对。

最低标准：提取源文件文本与输出文件文本，对比是否一致；允许的常见无害差异仅限末尾空行、连续空格归一等排版副作用。

推荐核对脚本：

```bash
python3 - <<'PY'
import subprocess, re, difflib

def norm(path):
    txt = subprocess.check_output(['textutil', '-convert', 'txt', '-stdout', path], text=True)
    txt = txt.replace('\r\n', '\n').replace('\r', '\n').replace('\xa0', ' ')
    lines = []
    for ln in txt.split('\n'):
        s = ln.strip()
        if re.fullmatch(r'PAGE\s*\d*', s):
            continue
        lines.append(s)
    while lines and lines[-1] == '':
        lines.pop()
    return lines

src = norm('source.doc')
out = norm('formatted.docx')
print('same_text=', src == out)
for line in difflib.unified_diff(src, out, fromfile='src', tofile='out', n=1):
    print(line)
PY
```

## 执行时的提问规则

只有当以下问题会明显改变版式时才问：

1. 这是普通公文、红头文件、信函式公文还是上行文？
2. 是否需要保留原单位专用模板、Logo、套红、页眉页脚？
3. 是“只刷新格式”还是允许顺手微调明显断句/错分段？
4. 是否需要预留盖章区，还是只做无章电子文稿版？

其余情况默认按“**普通机关公文、只刷新格式、不改正文内容、输出新 docx**”执行。

## 推荐对外汇报方式

完成后要主动告诉用户：

- 输出文件路径
- 是否保持原文一致
- 做了哪些格式刷新
- 哪些部分因原文信息不足采用了保守处理
- 若未严格复刻红头/印章/白体页码，明确说明原因

## 实验发现（已验证）

1. 在同一份 legacy `.doc` 样本上，`docx` 底座路线与 `word-doc` 底座路线都可以做到**正文零改动通过**，但版式表现不同。
2. `word-doc` / `python-docx` 路线通常更适合“中文公文材料重建”，页面收敛度和整体公文观感通常优于 `docx-js` 路线。
3. `docx` 底座路线虽然整体公文观感略弱，但在某些环境下，一级标题的视觉字重反而更稳定，不容易出现“看起来像被加粗”的问题。
4. **规则正确不等于视觉结果正确。** 即使代码里没有设置 `bold=True`，若最终字体被 Word / LibreOffice / PDF 导出链替换，一级标题仍可能呈现“视觉偏重感”。因此验收时不能只看代码或抽取文本，必须看最终渲染结果。
5. 对机关公文刷新任务，若用户对“黑体绝不能看起来偏粗”特别敏感，除文本 diff 外，建议追加 PDF 首屏视觉复核或字体落地检查（如 `pdffonts`）。

## 典型 pitfalls

1. **绝对不要把纯文本直接写成 `.doc`。** 这会生成损坏文件。
2. **旧 `.doc` 先用 `textutil` 读。** `python-docx` 不能直接读 `.doc`。
3. **中文字体必须设置 `w:eastAsia`。** 否则 Word 中会回退到错误字体。
4. **不要把用户原文“顺手改漂亮”。** 机关公文首先看规范和一致，不看文采发挥。
5. **不要保留“主题词”旧格式。** 2012 年后的规范已经取消主题词。
6. **不要随意补签发人、密级、紧急程度。** 原文没有、用户未说明时，宁缺毋造。
7. **联合行文、上行文、信函式公文** 的版式差异很大；看不准就问。
8. **不要覆盖原文件。** 永远另存为新 `.docx`。
9. **生成后一定做文本比对。** 格式刷新成功不等于内容没丢。

## 最小交付标准

一次合格的“公文格式刷新”至少应满足：

- 成功读取原文件
- 成功输出新的 `.docx`
- 标题/正文/层级/附件/落款位置基本规范
- 中文字体不乱
- 原文内容未被擅改
- 已做文本一致性核对
- 已向用户主动汇报输出路径与限制说明
